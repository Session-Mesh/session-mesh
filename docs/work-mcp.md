# The `work-mcp` server

`work-mcp` is a stdio MCP server with 17 `work_*` tools. It sits on the worklog library (`ocaml/worklog/`, data format in [worklog-format.md](worklog-format.md)) and lets an agent read and write project tracking: tasks, projects, products, the sessions that worked on them, and non-blocking questions. Its sources are `ocaml/work_mcp/` (library `work_mcp`, executable `work-mcp`).

The server is a separate program from `mesh-board-mcp` and does not talk to the Mesh: no port, no HTTP, no network. Registering it with an agent is a separate step that belongs to the owner; nothing in this repository does it.

## What it reads from the environment

| Variable | Use |
|---|---|
| `WL_HOME` | The data repository. Without it: `~/worklog-data`, else the older `~/worklog` (the library's discovery). |
| `MESH_SESSION` | The session name the Mesh gives each session. It becomes the `session` of every event the server writes. A value the library refuses (allowed: `A-Z a-z 0-9 _ . : -`, not starting with `-`) is ignored and the session is recorded as unknown: nothing is linked or attributed, and the server does not fall back to `WL_SESSION` or `CLAUDE_CODE_SESSION_ID`. The same holds when the library refuses the identity for another reason (for example an invalid `WL_AGENT`). Every write made that way carries a `write_warnings` entry saying that the identity was not resolved, so the caller learns that its write has no session and no agent. When `MESH_SESSION` is unset or empty, the library's own variables apply (`WL_SESSION`, `CLAUDE_CODE_SESSION_ID`, `OPENCODE_SESSION_ID`). |
| `WL_AGENT`, `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `OPENCODE_SESSION_ID`, `CODEX_THREAD_ID` | The agent kind (`claude`, `opencode`, `codex`). The Mesh sets no variable for it, so the server reads the markers the agents leave; `WL_AGENT` is the explicit override and wins. A configuration variable such as `CODEX_HOME` or `OPENCODE` is not a marker, because users export them without running that agent. With a session but no marker the agent is `agent`. |
| `WL_HOST`, `WL_NOW`, `WL_LOCK_TIMEOUT` | Read by the library as `wl` does. |

The Mesh session token is never read, logged, stored or returned. The library runs `git` with the whole environment, so the server also empties `MESH_SESSION_TOKEN` in its own process at start: no `git` child inherits it (the tests run a stand-in `git` that logs its environment and check this).

Identity is attribution, not authentication: see "Trust model" below.

## The data repository

At first use, when no repository is found and the place the library looks first (`WL_HOME`, else `~/worklog-data`) is an empty directory, or does not exist but its parent directory does, the server creates it (one level only: a misspelt `WL_HOME` such as `.../missing/a/b` is refused with the `repository` error and no directory is made; create the parents yourself) with the library's `init`: a minimal `taxonomy.yaml`, empty `tasks/` and `events/`, and a local git repository without remote. It never overwrites: a directory holding anything else, or two valid default repositories, is an error and nothing is written. Writes are committed locally by the library, as `wl` does; nothing is pushed. If the creation itself fails (for example the parent directory is not writable), the error says so ("could not be created at first use") instead of repeating "no repository found". Two servers that start together on a new directory both succeed: the second reads again for up to two seconds while the first finishes. It only waits when the directory looks like a repository being created (empty, a `taxonomy.yaml.tmp`, or a `taxonomy.yaml` without all of `.git`, `tasks` and `events`); any other existing directory, for example a plain git checkout holding a `.git`, `events` or `tasks`, fails at once.

## Tools

Ids: `T-` plus hex is a task, `P-` a project, `B-` a blocker, `N-` a question. A unique prefix of an id is accepted where a task or project is named.

| Tool | What it does |
|---|---|
| `work_resume` | Start-of-session briefing: tasks here (linked to this session, repo and branch, or folder), in progress, blocked or waiting, stale (5 days), due within 7 days, plus the open question count and this session's questions with their answers. Filters: product, project, track, owner; `stale_days`, `show_all`. |
| `work_list_tasks` | Filtered list: product (with descendants), project, status, track, owner, session, category; done and dropped hidden unless `include_closed` or a status is given. |
| `work_get` | One task or project by id: fields, blockers, linked sessions, notes (the body of the task file) or tasks, newest events, questions. |
| `work_list_projects` | Projects with progress (done over total). |
| `work_list_products` | The product tree with parents and open task counts. |
| `work_add_task` | Optional `request_id`. Creates a task; `notes` is the body of the task file, written once. Links the calling session. |
| `work_add_project` | Creates a project in a product. |
| `work_add_product` | Adds a product to `taxonomy.yaml`, optionally under a root. No rename, move or deletion. |
| `work_update` | `set` (scalar fields, `null` clears where allowed), `add` and `remove` (list fields) on a task or project. Applied in that order, each under the repository lock; the first failure stops the rest and the error says how many were applied. No deletion: set `status` to `dropped`. |
| `work_log` | Optional `request_id` (see "Retried writes"). Appends `progress` (default), `note`, `decision`, `learning`, `risk`, `metric`, `mentoring` or `shipped` (with `date`), with `prov` `stated`, `inferred` or `confirmed`. |
| `work_block`, `work_unblock` | Opens a blocker (returns `B-...`) and resolves one; the result names the task by its full id even when called with a prefix. |
| `work_find_sessions` | Sessions linked to the tasks of a product (with descendants), project, track, or one task: name, agent, repo, branch, last activity, task ids. Never the folder: `repo` is the last component of the repository path (its name), or absent (also when the repository is the home directory itself, whose name would be the login). The full path stays in the data repository for `wl` and the interface. `include_closed` defaults to `true`; `false` is refused (see below). |
| `work_get_session` | The other way round: the tasks of a session, its newest events and its questions. The optional `agent` filters tasks, events and questions alike. Its `links` are this session's own (not the other sessions that worked on the same tasks). |
| `work_ask` | Records a non-blocking question: `text`, optional `task` (T- or P-), `options`, `assumption`, `request_id`. |
| `work_list_questions` | Questions with their answers, filtered by state (`open`, `answered`, `all`), task, session, or `scope` (`all`, `with_task`, `without_task`: the questions about no task or project; not combinable with `task`). |
| `work_open_view` | Validates its input (the target must exist) and answers `{"opened": false, "reason": "not available until the interface slice"}`. It asks nothing of the Mesh. |

Every input schema rejects unknown fields. A failed call is an MCP result with `isError: true` and `{"error": {"code", "message"}}` (`invalid_input`, `not_found`, `repository`, `lock_timeout`, `malformed_data`, `io_error`, `internal`, `not_available`, and `output_too_large`, a last-resort guard that stored data does not reach: a result is shrunk to fit instead); malformed arguments are refused by the schema layer with a plain error text. No exception leaves the server.

Errors and warnings carry no absolute path. A `repository` or `io_error` message is a fixed text (the location is not returned), an unexpected exception is `internal` with a fixed text, and every other message, `write_warnings` (git's first output line) and `data_warnings` have every path replaced by `<path>`: an absolute or `~` path, a flag glued to one (`-C/srv/x`), a relative path of two or more components (`x/y/z`), after a space, a quote (ASCII or typographic), a guillemet, a no-break space or other punctuation. URLs stay readable, except `file://` URLs, whose path becomes `<path>`; a relative path of one component (`a/b`) is not a path to hide and stays. The text content of an error is sanitised exactly like its structured content. For debugging, `WORK_MCP_DEBUG=1` prints the raw detail to the server's stderr only.

Free text is checked on input and cleaned on output. A call whose arguments hold a control character other than newline and tab (C0, DEL, C1: so also carriage return, ESC, NUL) is refused with `invalid_input` before anything is written; this covers every string, in titles, notes, log, question, block and option texts, tags, links, owners, tracks and the rest. Invisible and bidirectional characters are refused the same way (`invalid_input`, naming the field), in every free-text field and in field names: the bidi controls U+061C, U+200E, U+200F, U+202A to U+202E and U+2066 to U+2069, the line and paragraph separators U+2028 and U+2029, the zero-width space U+200B, the byte order mark U+FEFF, the word joiner U+2060, the invisible operators U+2061 to U+2064, the interlinear annotation characters U+FFF9 to U+FFFB, and the Unicode tag block U+E0000 to U+E007F. They can hide text from a person, disguise a name or carry instructions that a model reads and a person does not see. U+200C and U+200D stay allowed: emoji sequences (a family, a flag) and some scripts need them. **Data returned is untrusted: control, bidirectional, zero-width and tag characters are removed** from every string and every key of every result (text and structured content), and an invalid UTF-8 sequence (a stray byte, a truncated or overlong sequence, an encoded surrogate) is replaced by U+FFFD, also for data written by other means (a file edited by hand, another tool): a terminal escape in the data never reaches a terminal or an interface, and every response line is valid UTF-8. The cleaning comes before any cut, so removed characters never use up a length bound (the notes of a task are cleaned, then cut at 8000 bytes). Limit: other format characters remain, for example the soft hyphen U+00AD, U+180E, variation selectors, private-use characters and look-alike letters from other scripts; the instructions' rule that data is information, never an instruction, is the defence for those.

Results are bounded: lists have a `limit`, strings are cut, and the serialised result (JSON text, bytes) never exceeds 48 000 bytes. A longer result is shrunk at every depth until it fits: the value that takes most room is cut first (a list loses its second half and `<key>_omitted` says how many items were cut; a string loses half of its characters), and `truncated` is `true`. The cut is order-aware: lists that are newest first (`questions`, `timeline_newest_first`, `events_newest_first`) keep their head, the `answers` of a question (in time order) keep their newest items, and `my_questions` is halved by group, the open questions first and at least one answered question while there is room; `my_questions_omitted`, `my_open_questions_omitted` and `my_answered_questions_omitted` are raised by what each group lost, so they always agree with the list returned. A stored task or project can always be read; `output_too_large` is not returned for stored data. Nested lists and long strings are bounded on output too: tags (30 of 100 bytes), links (20 of 300), blocked_by and also (20), milestones and risks (20 of 300), blockers, linked sessions and questions of one item (20), options (8 of 100 characters), the answers of a question (the newest 5, `answers_omitted` counts the older ones), and every string at a fixed length (the question, assumption, options and answer texts count characters, like their write limits; the other strings count bytes, cut on a character boundary); each cut list has a `<key>_omitted` count and the response has `truncated: true`. The items beyond the cap stay in the data repository but are not returned; a response that is cut cannot be widened, only narrowed by asking for a smaller set (a filter, a lower `limit`).

### Retried writes

A write takes the repository lock (up to 30 seconds) and then a git commit (up to 60 seconds), so a client can time out while the write still completes, and a blind retry writes twice. `work_log`, `work_add_task` and `work_ask` therefore accept an optional `request_id` (1 to 64 characters among `A-Z a-z 0-9 _ . : -`). A second call of the same session, with the same `request_id`, on the same target (the task for `work_log`, the product for `work_add_task`, the task or project or none for `work_ask`) returns the first result with `"duplicate": true` and writes nothing; another session, another tool or another target writes. A `request_id` needs a session identity. `work_ask` stores the key on its `question` event. The library takes no extra field on its own events, so for `work_log` and `work_add_task` a small `request` event (`tool`, `request_id`, `target`, `result`) is written right after the write: a crash between the two writes leaves a write whose retry is not recognised, and `wl` warns about the unknown type like it does for `question` and `answer`. Without a `request_id`, check with `work_get` before repeating a write. `work_update` is not covered: its `set` and `add` operations are idempotent, a retried `remove` fails with "not in".

The window of the guarantee, exactly: the write, the session link and the `request` marker are three separate transactions, in that order. A retry is recognised only once the marker is written. If the marker's transaction fails (a lock timeout is the very condition that makes a client time out; the call then carries a `write_warnings` entry "the request_id could not be recorded, so a retry of this call would write again"), or the server stops between the write and the marker, a retry with the same `request_id` writes a second time. The lookup and the write do not run under one lock either, so two server processes with the same session name could both write; requests of one process are handled one after another, so a same-process retry is safe. `work_ask` is not affected for its own retries (the key is stored on the question in the same transaction as the question). When a call timed out or carried that warning, check with `work_get` or `work_list_questions` before retrying.

### Session links

The library links a session to a task when it logs. The server goes further: every write that reaches a task (`work_add_task`, `work_update`, `work_log`, `work_block`, `work_unblock`, and `work_ask` with a task) links the calling session once, in a separate transaction after the write (a failed link is reported as a `write_warnings` entry, not as a failed write). A session that writes nothing on a task is not findable: the data repository does not record which sessions are open. `work_find_sessions` therefore cannot filter on "open"; `include_closed: false` returns `not_available` instead of a silently different answer.

## Questions (our extension)

Two event types are added to the log. The library ignores unknown types with a warning, so `wl` keeps reading the files, but it is not silent: `wl` warns once per event on stderr (`wl: warning: ignoring unknown event type "question"`, the same for `answer` and for a `request` marker, and `event for unknown task N-... ignored` for a question about no task, whose `task` field holds the question id). With dozens of questions every `wl` command prints dozens of warning lines. This is an extension on our side and the noise is to be reported to the author of `wl` (an ignore list or a namespaced event type would silence it). The server's own read warnings drop exactly these messages from `data_warnings` (the tests check that no `data_warnings` appears once questions, answers and request markers exist).

- `question`: `task` is the task or project the question is about, or the question id when it is about none; `id` (`N-` and eight random hex digits, not `Q-`, which `wl` uses for proposals; the six-digit ids of the first version are still read), `text` (at most 2000 characters), optional `options` (at most 8, 100 characters each) and `assumption` (at most 1000), plus `agent`, `session` and the optional `request_id`. If two question events (written on two hosts, then merged) use the same id, the first by time and host defines the question, the other is ignored and every read reports the collision in `data_warnings`.
- `answer`: the same `task`; `question`, `text` (at most 2000) and `by`. An answer is matched to its question by id after all questions are read, so an answer that sorts before its question (same second, another host) still attaches.

`work_resume` shows this session's questions in `my_questions`: the open ones first (newest first), then the ones answered in the last 14 days, ten at most. Slots are reserved so that neither group hides the other: with many of both, 6 open and 4 answered are shown (a group that needs fewer slots leaves them to the other). `my_questions_omitted` counts the rest, `my_open_questions_omitted` and `my_answered_questions_omitted` split that count. An old unanswered question is never pushed out by newer answered ones, and an answer is never hidden by ten open questions. A question event that cannot be read (no text, or an id that is not `N-` and eight lowercase hex digits) is not dropped silently: every read reports it in `data_warnings`. So is an `answer` event that names no question, or that lacks a question id or a text ("answer event ignored: ..."). The match is by session name: a session name that the Mesh reuses inherits its still-open questions, but not old answered ones.

No tool writes an answer. `Work_questions.answer` in the `work_mcp` library is the writer; the interface calls it with the owner's identity. The tests check that the tool list has no answering tool and that no tool-call route produces an `answer` event.

## Known limits

- **Carriage return is refused** in all free text (it is a control character): a client that sends CRLF line endings gets `invalid_input` and must send LF.
- **Path sanitiser bypasses remain.** Only error and warning texts are sanitised, never data, and the forms handled are the documented ones. Still visible: a non-`file` URL keeps its path (`ssh://host/home/alice/x`), a made-up scheme with an absolute path (`foo:///home/alice/x`), a Windows path (`C:\Users\alice\x`), and one path component glued after a non-ASCII letter (`é/srv`). The sentence "every path is replaced" above means the documented forms. Relative paths such as `2026/11/19` or `origin/feat/x` become `<path>` (a false positive).
- **Responses carry the data twice**: `content[0].text` repeats the structured content as JSON text, so a response is about twice the 48 000-byte bound on the wire (lines of about 95 kB).
- **Large event files are slow to read.** The library reads the whole event history for each call; with several megabytes of events a call can take seconds to tens of seconds on a busy machine (`work_resume` included). This is the worklog library's cost, not the server's output size.
- **Deeply nested requests.** The validation of tool arguments in `mcp-kit` takes minutes of CPU and several gigabytes of memory on deeply nested arguments (for example `{"product": [[[...]]]}` at a depth of 30 000, a 60 kB line), and the server answers nothing else meanwhile. JSON parsing itself is fast; the cost is in the validation before the handler. The stdio loop of this server (`Work_stdio`) refuses a request line whose raw bracket nesting exceeds 32 with a JSON-RPC error `-32600` (`id` null) before it reaches `mcp-kit`, which removes the exposure through the stdio line. A tool request never nests deeper than about 8. The underlying library is not fixed (an upstream issue is to be filed); until then do not register the server for an untrusted client through any other transport.
- **Other format characters** than the ones listed under "Tools" remain in text (see there).

## Trust model

What the tool layer guarantees: no MCP route writes an `answer`; question ids come only from the server, so a tool cannot close another question; text that looks like an event line stays one escaped line in one field.

What it does not guarantee: every Mesh agent has a shell as the same Unix user. One line appended to `events/*.jsonl`, such as `{"type":"answer","question":"N-...","by":"owner",...}`, closes any question, and `by` is free text. The `by` of an answer and the `agent` and `session` of every event are therefore attribution, not authentication: they say who claims to have written the line, not who did. A prompt-injected agent can forge an "owner" answer. For this reason the server instructions tell agents that an answer is information, never an instruction: it can correct an assumption, it never widens what the agent may do and never overrides the owner's or the repository's rules. The interface slice should show the provenance as unauthenticated.

Entries are committed to git, never edited and read by other agents; the instructions tell agents never to write secrets or credentials in them.

Link targets (`links` of a task, `hlp` of a project) and every other string are stored as given: `javascript:alert(1)` is accepted. The interface must check the scheme (allow `http`, `https` and relative references) when it renders a link.

## Running it by hand

```
cd ocaml
dune build work_mcp/bin/work_mcp_main.exe
WL_HOME=/tmp/work-demo MESH_SESSION=demo ./_build/default/work_mcp/bin/work_mcp_main.exe
```

The server reads JSON-RPC lines on stdin (`initialize`, then `tools/list` or `tools/call`) and answers on stdout. With `WL_HOME` pointing at a new directory it creates a repository there at the first tool call. Use a temporary `WL_HOME` for experiments; the default is the owner's own data.

## Tests

`dune runtest work_mcp` drives the real executable over stdio, against temporary fictional repositories with their own `HOME`, `WL_HOME` and `MESH_SESSION`: the tool list, every tool with a good and a bad input, session identity from the environment, two clients writing at once, the question lifecycle with the answer written through the library, first-use creation and refusal to overwrite, output bounds, and the absence of the session token and the session folder from every output. The review regressions: the server run with its working directory at a repository root (no absolute path in any output, `repo` is a name), nested lists and hand-written questions over the bounds, error and warning messages without paths (a directory that is not a repository, a path below a file, an uncreatable repository, a failing commit through a stand-in `git`), no session fallback and no guessed agent, the token absent from the environment of every `git` child, retried writes with a `request_id`, question ids and collisions, an answer sorting before its question across two hosts, no `wl` warning noise in `data_warnings`, the `scope` filter, `my_questions` ordering, full ids from `work_block`, the `agent` filter of `work_get_session`, a failed link in the warnings, and two servers creating the repository at once. The second review's regressions: control characters refused on input and removed on output, the output bound at every depth, cuts on character boundaries (a response line is valid UTF-8), the newest answers, `my_questions` slots, the path sanitiser forms, the identity warning, a foreign directory failing at once, no chain of parent directories, `links` of one session, malformed question ids, character limits and the home directory as repository. The third review's regressions: the output shrink keeps the newest answers and the open questions with consistent counters, invalid UTF-8 in a hand-written task body, invisible and bidirectional characters refused on input and removed on output (emoji ZWJ sequences accepted), notes cleaned before the cut, a stricter absolute-path helper, an orphan answer reported, and the nesting guard of the stdio loop.
